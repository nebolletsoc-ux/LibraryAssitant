--- Technical debt (added after TBR rework, September 2026) ---
No automated test suite, RESOLVED, A real pytest suite now exists and is maintained (84 tests, all offline/mocked) covering books/libraries/import-csv/check-all/clear/synopsis endpoints and the list + book-detail filter logic. Duplicate Book rows for the same title, medium, Different search results/editions (e.g. "The Lager Queen of Minnesota" vs "The Lager Queen of Minnesota: A Novel") can create separate Book rows with separate synthetic ISBNs, so the same book can appear twice in the TBR list. Single hardcoded user (user_id=1), medium, Every model and endpoint assumes one user. Any real multi-user deployment needs an auth layer and per-user scoping instead of the hardcoded default.

Open Library search has no caching or backoff, medium, Rapid repeated searches during testing produced real 503s from Open Library. The app now surfaces a clear "temporarily unavailable" message, but there is no client-side rate limiting, retry/backoff, or short-lived caching of recent queries.

--- Revision 04 Sep 2026 (async availability scan — mobile fix) ---
Refresh availability failed on mobile, RESOLVED, On the Render deployment, POST /api/books/check-all BLOCKED the HTTP request until all books were scraped — over 2 minutes on the deployed DB (143 books, Oakland + Berkeley + Hoopla enabled), which mobile Safari aborts (~60s) and even desktop tolerates only quietly. Diagnosed live: healthz/tbr/books/libraries/search all returned 200 fast, but check-all exceeded the probe's 120s. The scan is now ASYNC: POST /api/books/check-all returns 202 immediately with a job_id (or 400 if no libraries are enabled), the scan runs in the background on the shared 8-worker pool, and GET /api/books/scan-progress/<job_id> reports {id, total, processed, checked, failures, done}. The frontend polls every 2s and the status bar shows live progress ("Scanning 43 of 148 books · 36s") with an elapsed timer; on completion the button resets, the bar hides, a toast reports "NNN books checked" (or the failure count), and the list reloads. Tapping Refresh while a scan is already running resumes watching the in-flight job (already_running) instead of double-scanning. Scans are serialized server-side (one active job at a time). Verified end-to-end in headless Chrome at a mobile viewport (390x844): 148 books render, refresh shows ticking progress to 148/148, then bar hides / button re-enables / list reloads, no JS exceptions; live checks completed 148/148 with 0 failures on the real network.
Status-bar progress flicker fixed, RESOLVED, scanStatus() previously captured its text in a per-call closure while the 1s ticker kept re-rendering the ORIGINAL message, so live "Scanning N of M" updates would flash back to a static "Scanning availability" every second. The ticker now reads a shared scanStatusText, so progress displays steadily.
Overlapping refresh clicks, RESOLVED, Each Refresh click owned its own poll timer locally, so a second click could not stop the first loop — orphaned pollers kept hitting a finished job forever (observed as endless scan-progress requests in the server log across headless tabs). The poll timer is now module-scoped (scanPollTimer, single active loop; a new click clears the old one) and every exit path resets the button/label/bar.
